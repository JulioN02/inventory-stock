Descripción del proyecto

No es el típico CRUD de inventario.

El stock nunca se establece: se deriva del libro mayor de movimientos. Cada movimiento es una fila inmutable y el saldo es una vista agregada.

Funciones / capacidades

Lo que demuestra el proyecto, más allá de un ABM de productos.

Transacciones

Atomicidad de operaciones multi-tabla: si una parte falla, no queda ningún cambio a medias.

Consistencia

Invariantes de stock bajo concurrencia; imposible vender stock inexistente (LAB-01).

Idempotencia

Reintentos seguros sin efectos duplicados mediante claves de idempotencia (LAB-02).

Auditoría

Quién, cuándo y qué cambió, de forma inmutable y append-only (LAB-08).

SQL

Consultas parametrizadas, joins de RBAC y la vista agregada stock_levels.

Permisos

RBAC verificado por request sobre módulos y operaciones.

Fundamentos

Las reglas de dominio que sostienen el sistema.

  • Libro mayor inmutable: los movimientos nunca se editan ni se borran.
  • Cada movimiento es una fila con quantity > 0 y un sign de ±1.
  • stock_levels es una vista: SUM(quantity * sign).
  • Un pg_advisory_xact_lock por clave (product, warehouse) evita sobregirar el stock bajo concurrencia.
  • Idempotencia con idempotency_key + request_hash canónico (SHA-256): un reintento devuelve 200 y una operación nueva, 201.
  • La auditoría append-only se garantiza con el trigger de base de datos forbid_ledger_mutation.

Arquitectura

Un monolito modular organizado por vertical slices, con contrato API-first.

  • Monolito modular + vertical slices: cada módulo agrupa su dominio, su servicio y sus rutas.
  • API-first: el contrato HTTP se define antes que la interfaz y es la fuente de verdad.
  • Un solo origen: Express sirve el SPA compilado, sin CORS entre frontend y backend.

Módulos

Seis módulos con responsabilidades claras.

Módulo Rol
Products Catálogo de productos
Warehouses Ubicaciones físicas de almacenamiento
Movements Libro mayor inmutable: recepción, venta, transferencia y ajuste
Stock Estado derivado de los movimientos (vista SQL)
Auth / RBAC Login, refresh rotativo y 13 permisos sobre 4 roles (admin/operator/viewer/auditor)
Audit Auditoría append-only de eventos de dominio y autenticación

Modelo de datos

Tablas normalizadas y una vista para el saldo derivado.

Tablas

  • users
  • roles
  • permissions
  • role_permissions
  • user_roles
  • refresh_tokens
  • products
  • warehouses
  • movements
  • audit_log

Vista

stock_levels = SUM(quantity * sign)

La tabla products no tiene columna de cantidad: el stock siempre se calcula desde los movimientos.

API

Superficie HTTP del sistema, agrupada por recurso.

  • GET /api/health
  • POST /api/auth/{register,login,refresh,logout} — register solo para administradores.
  • GET/POST/PATCH/DELETE /api/products
  • GET/POST/PATCH/DELETE /api/warehouses
  • POST/GET /api/movements, POST /api/movements/transfers, POST /api/movements/adjustments
  • GET /api/stock, GET /api/stock/low
  • GET /api/audit

Todas las rutas protegidas verifican permisos por request.

Cómo correr

Requiere Docker y Node.js.

docker compose up -d          # PostgreSQL 16 (puerto 55434)
npm run migrate               # migraciones
npm run seed:admin            # bootstrap del admin
npm run dev:api               # Express 5 en http://localhost:3000
npm run dev:web               # Vite + React 19 en http://localhost:5173
npm test                      # 138/138
npm run typecheck

Copia backend/.env.example a backend/.env antes de correr el backend.

Labs

Los ejercicios que dieron forma al sistema.

LAB-01 · Race Condition

Consistencia de stock bajo concurrencia: el advisory lock por producto y almacén impide vender stock inexistente.

LAB-02 · Idempotency

Operaciones repetidas sin efectos duplicados: la clave de idempotencia y el hash del request detectan reintentos.

LAB-08 · Audit Trail

Auditoría inmutable: el trigger de base de datos rechaza cualquier mutación del libro mayor y del log de auditoría.
